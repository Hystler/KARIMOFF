# Kitchen Pilot: Stations and Inventory

## Policy and Rollout

- New migration: `supabase/migrations/20260911163830_kitchen_stations_and_pilot_inventory_policy.sql`.
- `kitchen_sla_settings.inventory_shortage_policy` defaults to `allow_negative`, including existing location settings. Locations without a settings row use the same explicit pilot default.
- No new environment variables. Do not enable `TEST_ORDER_MODE` for normal pilot orders.
- Switch a location to `block` in `/admin/kitchen` to restore strict shortage rejection. This changes future deductions, not completed accounting or existing negative balances. Settings remain staff/location-scoped and audited.
- Apply the migration before serving the updated kitchen code. The runtime migration script includes schema/function postconditions and respects its existing read-only mode. This task did not deploy or change shared production/test databases.
- The final migration was applied/reapplied only to the new disposable database at `127.0.0.1:55440`. Its setup ledger may have the earlier file checksum; do not rerun historical migrations to work around that difference.

## Transition Trace

`KitchenWorkspace` station form -> `transitionKitchenOrderAction` -> server maintenance/session/role/location checks -> `transitionOrder` locks the order and checks test/production isolation -> `set_order_kitchen_station_status_atomic` -> final station calls the canonical `set_order_kitchen_status_atomic` -> `set_order_status_staff_atomic` performs accounting.

The existing SQL had no per-line kitchen progress; `product_ingredients.station` describes recipe steps, not employee completion. Paid YooKassa order lines are immutable. Progress therefore lives in a new RLS-protected `order_item_kitchen_state` relation keyed by the existing order item ID, without editing commercial snapshots.

Exactly two work stations:

- `main`: burgers, shawarma, rolls and hot dogs, based on category. SQL and the JavaScript queue fallback both recognize `Хот-Доги`, `хот дог`, `хотдог`, `Hot Dogs` and `hot-dogs`.
- `snacks`: snacks plus drinks, sauces, unknown categories and packing. No third completion gate.

The station is captured when a new order line is created. Existing orders without kitchen-state rows are adopted lazily using their existing overall progress. Each station changes only its own lines. The All view has explicitly station-labelled commands, not a blanket mixed-order Ready command. A legacy whole-order Ready call is rejected for unfinished mixed-station work; single-station compatibility is preserved.

Both employees lock the same parent order row before updating progress. Partial completion leaves the overall order cooking, without stock/loyalty/fiscal completion. The final station runs the existing completion path transactionally. Duplicate or delayed station starts/Ready commands do not regress progress or repeat events/accounting. Partial progress emits an outbox event so the other screen refreshes.

## Accounting and Protection

The previous staff completion function aborted on a shortage. In pilot mode it now records the complete existing recipe/modifier snapshot requirement as a sale movement and subtracts the full amount from inventory. Missing balance rows are initialized before ordered row locking. Existing negative balances remain negative; no clamping or fabricated stock receipts are used.

The unique `order_inventory_deductions.order_id` record and parent/ingredient locks remain authoritative. Shortage details and the effective policy are included in the completion audit; warnings are returned to the kitchen. Strict mode rolls back the final station, balances, movements and completion together.

To represent consumption below zero, the inventory CHECK no longer forbids negative `current_quantity`. The existing nonnegative checks for `reserved_quantity`/`min_quantity` remain. Production and manual-writeoff SQL shortage guards are unchanged. Existing balances are global across locations; a deficit generated by a pilot location is visible to strict locations too.

Payment-required online admission, paid commercial-line immutability, POS payment-before-handout, fiscal settlement generation, role/location restrictions and test-order accounting suppression are unchanged. Loyalty earning/reversal SQL was retained verbatim.

## UI

`KitchenWorkspace.module.css` is self-contained; no global CSS, POS or inventory/production UI was edited by this task. Desktop populated queues divide available width; empty queues are 140px. Cards use a responsive grid inside independently scrollable queues. Queue height is measured below the actual header, with a 160px minimum. At 960px and below, full-width sections use normal page scrolling. Station selection persists using `karimoff.kitchen.station.v1`; blocked browser storage falls back to All without affecting operation.

## Remaining Limitations

Negative balances require real inventory reconciliation. Returning to strict mode does not repair deficits or recalculate old deductions. Products without a recipe retain the existing explicit missing-composition warning, not invented consumption. Station assignment follows product category; existing persisted assignments intentionally do not move when the catalog is later edited. Real provider calls and live operational orders were not exercised. No commit, push or deploy was performed.
