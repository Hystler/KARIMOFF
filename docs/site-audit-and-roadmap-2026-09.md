# KARIMOFF: аудит и план развития

Дата: 8 сентября 2026. База разработки: `d2e4095873ab207e85648cf08e4126d658d697b7`, отдельная ветка `codex/planning-notifications-audit`.

## Главное

Проведён аудит кода, безопасные чтения production, изолированные проверки PostgreSQL, браузера и нагрузки. Реализованы план закупок, операционный экран уведомлений, гостевой вход только через мессенджеры и исправления оплаты. Это не сертификат исправности всех production-данных и не подтверждение реальной фискализации.

Production-код, его переменные окружения и бизнес-данные в этой работе не изменялись; платежи, возвраты, складские движения и рассылки не запускались. Просмотр `/login` выполняет штатную подготовку технического login attempt, но подтверждение личности не выполнялось. Commit/push/deploy не выполнялись. В локальной отдельной PostgreSQL есть только синтетические данные. Старые пользовательские файлы `outputs/` сохранены; каталог исключён из Docker-контекста, чтобы экспортированные данные не попадали в сборку.

## Реализовано

### План закупок

Маршрут: `/admin/analytics/planning`, вкладка «План закупок» в аналитике. Доступ: owner/admin, поскольку текущий склад общий и не имеет полноценного распределения остатков по точкам.

- Среднее число заказов и количество каждого блюда за день.
- Горизонты закупки: 1, 2, 3, 7 и 14 дней; история 4, 8 или 12 полных недель до сегодняшнего дня, время Москвы.
- Прогноз учитывает день недели: ближайшая суббота рассчитывается по прошлым субботам, а не по среднему понедельнику. Дни без продаж входят в знаменатель.
- Блюда раскладываются по действующим базовым рецептурам; граммы, миллилитры и штуки не смешиваются.
- Нетто рецептуры переводится в закупочное брутто один раз: `нетто / (1 - отходы / 100)`.
- Доступно = учётный остаток минус резерв. Показаны ориентировочные дни до исчерпания.
- Закупка = потребность на выбранный период и страховой запас + минимальный остаток - доступное. Отрицательная закупка заменяется нулём; количество округляется до упаковки, если размер известен.
- Есть сумма закупки по известным ценам и явные предупреждения: нет остатка, цены, сопоставления или полной рецептуры. Неполное блюдо не раскладывается частично с ложными «100% покрытия».
- Источник продаж: существующая canonical analytics, с её исключением test orders и подтверждённых дублей. Завершённые продажи с возвратами исключены из этой первой модели, что указано на экране.
- Никаких автоматических закупок, списаний или изменений остатков при просмотре.

Это базовый прогноз, не полноценный MRP. Он пока не учитывает модификаторы, сезонность, промо, срок годности, поставки в пути и срок доставки. Неизвестный фактический остаток нельзя заменить прогнозом. При пропусках Evotor история может быть неполной, поэтому актуальность синхронизации важнее усложнения формулы.

### Уведомления

Маршрут: `/admin/notifications`, раздел «Уведомления». Есть агрегаты, последняя активность, зависшие записи, ошибки, список последних 50 доставок и безопасный повтор одной записи после исправления конфигурации. Повтор не отправляет сообщение непосредственно из браузера, проходит серверную проверку прав и аудит.

Исправлены обработка ответа MAX, потеря результата после успешного POST, зависшие попытки, лимит повторов и безопасное использование Telegram-адресата. Для Telegram сохраняется отдельный `id` из проверенного ID token в `metadata.telegramBotUserId`. `sub` остаётся идентификатором входа и не превращается в адресата сообщений. Существующая identity обогащается при обычном повторном входе; бот и аккаунт не меняются. Основание: [официальная структура Telegram User Data и write scope](https://core.telegram.org/bots/telegram-login#user-data-structure).

В production подтверждено только наличие/отсутствие настроек, без вывода значений:

| Проверка | Результат |
| --- | --- |
| `ORDER_STATUS_NOTIFICATIONS_ENABLED` | Выключено |
| `TELEGRAM_BOT_TOKEN` | Не задан |
| `MAX_BOT_TOKEN` | Задан, доступность отправки не проверена |
| Telegram OIDC | Настроен; не заменяет токен Bot API |

Поэтому обещать, что сейчас гостям приходят сообщения «Заказ готов», нельзя. До включения нужно проверить накопленную очередь и не разослать старые события. Подробные ограничения, согласия и порядок активации: [аудит уведомлений](audit-2026-09-notifications.md).

### Вход и корзина

- На гостевом `/login` и `/register` оставлены Telegram, затем MAX. SMS и телефонно-парольной формы нет.
- Телефоны, проверки номера, аккаунты, контакт для чека YooKassa и парольный вход персонала сохранены. Legacy backend-функции не удалены вместе с данными.
- Нельзя отключить последний доступный мессенджер, даже если в старом профиле остался password hash.
- Существующие протоколы Telegram/MAX, координаторы возврата и безопасный `returnTo` сохранены. Новое поле Telegram используется только для адресата уведомления.
- Нерешённая попытка оплаты не получает новый ключ из-за 15-минутного таймера.
- Корзина, изменённая пока создавался платёж, не очищается после подтверждения старой оплаты. При потере снимка очищение запрещено.
- Опрос результата платежа ограничен 8 секундами на запрос; сетевой обрыв не объявляет оплату неуспешной и не оставляет вечный зависший запрос.
- Независимые вкладки пока могут создать разные осмысленные checkout attempts. Серверное восстановление незавершённой покупки между вкладками остаётся отдельным улучшением; одинаковая сумма не используется для автоматического объединения заказов.

## Существенные находки оплаты

1. Клиент отклонял фактический сохранённый ключ второго чека из-за двоеточий. Исправлено без смены существующих ключей; ограничение 64 символа и запрет перевода строки сохранены.
2. Неопределённый результат создания мог повторно отправляться после 24-часового окна идемпотентности провайдера. Теперь просроченная операция без provider ID останавливается для сверки, а известный provider ID проверяется через GET. [Контракт YooKassa](https://yookassa.ru/developers/using-api/interaction-format#idempotence).
3. Запоздавшие ответы могли откатить завершённый чек или вернуть уже возвращённую сумму в доступный остаток. Защита добавлена в приложении и отдельной миграции состояния возвратов. Миграция не применяется к production автоматически.
4. Отдельные чек предоплаты и чек зачёта при выдаче не являются двумя продажами. Return URL не подтверждает оплату; KDS запускается после серверной проверки. Тесты выполняют этот путь на mocks и локальной БД.
5. Поздний Evotor-документ исключается из выручки только при подтверждённой связи. Просто похожие сумма и время не доказывают дубль. Без реальной сверки provider/fiscal identifiers нельзя утверждать, что все фактические документы production не задвоены.

Сценарий «платёж прошёл, затем ready, затем handed_out, пришёл чек» нельзя проверить внешним GET страницы. Реальный платёж, доставка чека на email и конкретный третий чек в кабинете провайдера в этой работе не проверены. Все тестовые платежи подставные, без списания денег. Подробные доказательства и оставшиеся гонки: [платёжный аудит](audit-2026-09-payments.md).

Ошибки в этом срезе не объясняют отсутствие заданий. Требуется чтение connection status, активных jobs и `last_success_at`; никаких ручных sync/write не запускалось. **Evotor health не подтверждён.**

Никаких production credentials или реальных provider calls. GET только `/`, `/menu`, `/login`; это HTML, не полноценные браузерные сессии покупателей.

**Нельзя преобразовать эти 20 запросов в утверждение «сайт выдерживает N пользователей».** Пока не проверены длительная нагрузка, большие реальные объёмы аналитики, мобильные сети, изображения/CDN, SSE, реальная задержка провайдеров, PostgreSQL production и ограничения Timeweb proxy.

Следующая нагрузочная проверка: отдельная staging БД с обезличенной репрезентативной историей, 15-минутные ступени 10/25/50 активных сессий, смесь menu/detail/cart/status + отдельный небольшой поток admin analytics. Только тестовые провайдеры и заказы. Измерять p95/p99, долю ошибок, CPU/RAM, ожидание пула SQL и число SSE; остановить ступень при ошибках >1% или устойчивом ухудшении. Production намеренно не нагружать.

Что улучшать по измерениям:

- Freshness индикатор: last successful sync, количество сопоставленных товаров, возраст складских остатков. Приоритет выше новых декоративных графиков.
- Свернуть журналирование пустых 5-секундных YooKassa циклов в редкий heartbeat с сохранением событий ошибок/работы: иначе они вытесняют полезные логи. Код worker в этой итерации не менялся.
- SQL pool сейчас 10 на процесс; не поднимать лимит вслепую. Для тяжёлой аналитики оценить EXPLAIN и ожидания на репрезентативной истории, затем краткий кэш агрегатов с ключом прав/периода. Не кэшировать авторизацию и оплату публично.
- При росте реплик выделить workers из Next.js и контролировать общий лимит отправки, а не лимит каждого экземпляра отдельно.

### Кампании не равны уведомлениям о заказе

Требуются отдельные purpose/channel/bot consent, дата/версия текста, отзыв и suppression. Проверка согласия нужна и при выборе аудитории, и непосредственно перед отправкой. Telegram write scope разрешает боту писать, но сам по себе не заменяет выбор получать рекламу. Использовать существующий журнал legal consents, не копировать все identities в массовую очередь.

Предлагаемая модель: `campaigns` + `campaign_deliveries`, отдельно от статусов заказов; утверждённая версия текста, dedup на campaign/recipient/channel, общий лимит, тихие часы, RBAC/audit. Предпочтительный канал задаётся гостем; при двух привязках не отправлять рекламу сразу в оба мессенджера. Не хранить raw provider payloads и не делать чувствительные выводы о человеке. Схема и отправка кампаний пока не реализованы.

### Подготовка тестового выпуска, 9 сентября

Стенд `timeweb-cutover-test` (2587) использует ту же БД, что production. Для просмотра интерфейса без миграции общей БД добавлен `RUNTIME_MIGRATIONS_READ_ONLY=true`: schema startup только проверяет наличие прежних объектов, а data startup не меняет каталог и сопоставления. Если необходимой схемы нет, приложение не стартует. По умолчанию прежнее поведение production не меняется. Два дополнительных поведенческих теста проверяют отказ от записи и пропуск подключения data migration.

Тестовый выпуск должен сохранять `TEST_ORDER_MODE=true`, `PAYMENTS_ENABLED=false`, выключенные уведомления и Evotor worker. Это просмотр и проверка интерфейса на текущих данных, не окружение для реальных платежей, возвратов или изменения склада. Новая платёжная SQL-миграция в общую БД не применяется; полная проверка payment hardening остаётся на отдельной локальной БД. Для полноценного интеграционного стенда нужна отдельная БД.

Перед следующей реальной оплатой: reviewed migration/checkpoint, разбор существующих pending/error fiscal записей без новых ключей, решение оставшихся гонок settlement/refund, отдельный staging прогон, затем явно согласованный один реальный заказ и оплата самим пользователем. Проверить первый чек, ready без второго чека, handed_out со вторым чеком, одну revenue/KDS/inventory operation, фактическую доставку уведомления. Возврат только по отдельному разрешению. До этого **нет подтверждения готовности к новой реальной платёжной проверке**.
