# KARIMOFF POS: проверка на физической кассе

Подготовлено для общего `codex/final-combined-rc` от delivery RC `97258c5`
с финальным POS handoff `79e96ed`. Требуется Bridge **0.21 / code 21**;
точный APK и SHA-256 зафиксированы в отчёте общей интеграции.
Проводить платёж только после отдельного разрешения владельца. До этого шага ничего на
кассе не оплачивать. Проверка требует установки обновлённого Bridge и сервера в
разрешённом окружении; этот документ сам по себе ничего не развёртывает.

## До начала

1. На точке откройте KARIMOFF Bridge на Эвоторе и оставьте его на переднем плане.
   Нажмите «Обновить диагностику». Запишите модель и номер кассы, версию Bridge,
   название карточного исполнителя, банк и номер банковского терминала.
2. В KARIMOFF admin откройте «Интеграции → Эвотор». В блоке KARIMOFF Terminal
   Bridge проверьте точку, имя нужной кассы и «в сети». В блоке «Сопоставление
   Bridge и облачной кассы» выберите **именно эту физическую кассу** из облака
   Эвотор, сохраните привязку и запишите cloud device ID и store ID.
3. На планшете откройте `/pos`, выберите ту же точку. Проверьте, что нужная касса
   доступна; если их несколько, выберите её явно. При отсутствии касс кнопка
   оплаты должна быть недоступна. Не нажимайте «Отправить тестовый заказ» в
   блоке Bridge: это отдельный режим предпросмотра.
   Если другой планшет уже держит эту кассу, ожидается «Касса занята»; другая
   свободная касса остаётся доступной. Если выбранная касса пропала из сети,
   выбор не должен сам переключиться на соседнюю.
4. Подготовьте один недорогой товар с известной рецептурой и остатком. Для
   реальной оплаты не включайте тренировочный режим `TEST_ORDER_MODE`.

## 1. Успешная оплата — после отдельного разрешения

1. На планшете добавьте один товар. Запишите точку, сумму и выбранную кассу.
   Нажмите «Перейти к оплате» **один раз**. Запишите номер заказа.
2. На выбранном Эвоторе проверьте тот же заказ, состав, сумму и карточный
   исполнитель. На другой кассе задание появляться не должно.
3. Проведите оплату один раз. Сохраните банковский результат и фискальный чек.
   Запишите ФН, ФД, ФП, номер чека и время. При ошибке или задержке не начинайте
   новый платёж.
4. В POS дождитесь «Оплата прошла, ожидаем подтверждение чека» либо
   окончательного подтверждения. Если фискальные реквизиты задерживаются,
   заказ остаётся вне кухни; повторная оплата заблокирована.
5. После подтверждения фискальных данных проверьте ровно один заказ в
   `/kitchen`. В admin откройте «Интеграции → Эвотор → Цепочка POS и чека»
   и запишите:
   `order ID → payment ID → payment intent/bridge task ID → выбранная касса →
   cloud device/store ID → local receipt UUID → ФН/ФД/ФП`. На этой странице также видны сумма,
   статус и банковский ID/RRN, если его отдал SDK.
6. На кухне нажмите «Начать готовить», затем «Готово». В admin откройте
   «Склад → Движения»: одна операция списания для заказа. Строк ингредиентов
   может быть несколько.
7. В admin откройте «Интеграции → Эвотор» и нажмите «Проверить новые продажи».
   После синхронизации запишите cloud document ID. В «Сопоставление продаж»
   должна появиться подтверждённая связь этого чека с тем же заказом без
   ручного выбора. В «Аналитика → Продажи» должна быть одна продажа и одна сумма
   выручки. На странице «Цепочка POS и чека» проверьте также cloud device ID
   и store ID. Если облачный документ содержит несколько печатных групп,
   сверьте все группы в блоке «Печатные группы облачного чека»: ни одна не
   должна исчезнуть, а с заказом должна совпасть ровно одна группа по
   ФН/ФД/ФП. Повторите импорт: количество продаж и списаний не меняется.
   Если чек не связан, в «Сопоставление продаж» проверьте состояние:
   `unreconciled` означает отсутствие точного совпадения, `ambiguous` —
   несколько совпадений и обязательную ручную проверку.

Не считать сценарий пройденным, если связь возникла только по сумме, времени,
номеру позиции либо через ручное подтверждение.

## 2. Отказ или Cancel

1. Создайте другой небольшой заказ и отправьте на выбранную кассу.
2. Отмените выбор способа оплаты до денежной операции. Для отказа после
   банковского экрана отдельно проверьте в банке/Эвоторе, что списания нет.
3. В POS ожидается `cancelled`/`failed`; в `/kitchen` нет оплаченного заказа,
   в «Склад → Движения» нет списания, в аналитике нет продажи.
4. Если статус банковской операции неизвестен, ожидается `UNKNOWN`, а не
   безопасная отмена или автоматический повтор.

## 3. Обрыв связи и UNKNOWN

1. С сотрудником на точке согласуйте момент обрыва связи. Создайте отдельный
   заказ; разорвите связь только на согласованном этапе.
2. На планшете проверьте понятное `UNKNOWN` для неизвестного денежного
   результата. Если оплата уже подтверждена, ожидайте другое состояние:
   «Оплата прошла, ожидаем подтверждение чека».
3. Убедитесь, что новая банковская операция не запускается и касса остаётся
   занятой. Сначала проверьте прежнюю операцию в банке и закрытый чек на Эвоторе.
4. Восстановите сеть и откройте Bridge. Сохранённый результат должен уйти на
   сервер повторно, а фискальные реквизиты должны дочитаться по сохранённому
   UUID. Повторное получение callback не создаёт заказ/списание/выручку.
5. Если автоматического подтверждения нет, ответственный сотрудник запускает
   импорт Эвотор, сверяет закрытый чек на кассе и вручную вводит **ID уже
   импортированного документа, ФН, ФД и ФП**. Система требует точное совпадение
   этих реквизитов с импортом для нужной точки. Номер чека, сумма и время по
   отдельности не подходят. Пока доказательства нет, новый charge запрещён.
   Отправленный на кассу `UNKNOWN` нельзя вручную отменить для освобождения
   терминала только по предположению, что покупатель не заплатил.

## Критерий hardware acceptance

До импорта доказана цепочка `order → payment → intent/task → выбранная касса →
cloud device/store ID → local receipt UUID → ФН/ФД/ФП`; после импорта — `cloud document ID → та же
фискальная идентичность → автоматическая связь с тем же order`. Один KDS order,
одно списание при «Готово» и одна учитываемая продажа. Все три сценария
должны пройти на физической кассе.
