# Уведомления о заказах

KARIMOFF ставит транзакционное уведомление в очередь только при переходе canonical kitchen status в `ready` или `cancelled`. Тестовые заказы исключены. Очередь не меняет заказ, выручку, склад, KDS или фискальные документы.

## Доставка

- Telegram: официальный Bot API `sendMessage`. Login Library запрашивает scope `write`; для OIDC документация отдельно называет `telegram:bot_access`. Запрошенное разрешение не равно сохранённому доказательству его выдачи и не является согласием на рекламу.
- Telegram использует **только** `identity.metadata.telegramBotUserId`: parent/auth сохраняет это строковое поле из положительного safe-integer `claims.id` после проверки подписи. `provider_user_id=claims.sub` остаётся ключом входа и никогда не используется как fallback `chat_id`. Worker повторно проверяет формат и безопасный диапазон ID; отсутствие/некорректное значение останавливает доставку с `telegram_recipient_unverified`.
- Старые identities получат поле при следующем обычном входе в Telegram. При настроенном Telegram Login профиль позволяет повторно проверить Telegram через существующий поток: без Bot API ID показывает кнопку подтверждения, а с сохранённым ID — кнопку повторной проверки. При отключённой/некорректной конфигурации профиль объясняет, что повторная проверка недоступна. Привязка обновит метаданные только для той же Telegram identity; если вход выполнен под другим Telegram-аккаунтом, существующий способ входа останется без изменений и вернётся конфликт. Принудительное отвязывание и DB migration не требуются. Наличие Bot API ID само по себе не доказывает право бота писать; это проверяет отдельный адресный `sendMessage`.
- MAX: официальный `POST https://platform-api2.max.ru/messages?user_id=...`, bot token передаётся только в заголовке `Authorization`.
- Обе ссылки ведут только на HTTPS origin из `APP_ORIGIN` + `/profile/orders`; credentials, query, fragment, session ID, order token и PII в URL не передаются. Следование HTTP redirect при POST запрещено.

Официальные разделы:

- https://core.telegram.org/bots/telegram-login
- https://core.telegram.org/bots/api#sendmessage
- https://dev.max.ru/docs-api/methods/POST/messages

## Надёжность

`order_notification_deliveries` имеет unique constraint `(order_id, identity_id, event_type)`: это защита от повторной постановки, **не exactly-once доставка**. Worker забирает только `pending/retry` с числом попыток меньше восьми через `FOR UPDATE SKIP LOCKED`. Перед POST проверяются текущий статус заказа, `is_test=false`, действующая identity и её принадлежность тому же покупателю. Обновления результата ограничены текущей попыткой и состоянием.

429 и явный HTTP 5xx повторяются с ограниченным backoff, не раньше указанного `retry_after` / `Retry-After`. MAX учитывает секунды и HTTP-date; отсутствие заголовка даёт 30 секунд. При восьмой попытке повторы прекращаются. Для POST с HTTP 5xx остаётся риск дубля, поскольку гарантированная провайдерская идемпотентность здесь не установлена.

Сетевой обрыв, timeout/408, неполный успешный ответ и lease старше пяти минут означают неизвестный результат. Такие записи переходят в `permanent_failure` с безопасным кодом и **не отправляются повторно автоматически**. Старые `retry` после network/unknown failures также изолируются. Это сознательный выбор против дублей с возможной потерей доставки до ручной проверки, не гарантия доставки.

Успех требует `result.message_id` у Telegram или `message.body.mid` у MAX. Если провайдер принял сообщение, а сохранение результата упало, запись не переводится в `retry`; истёкший lease будет изолирован. Позднее подтверждение той же попытки может зафиксировать `sent`. Ошибки scheduler перехватываются; в журнал не попадают исходные исключения, provider payload, bot token или телефон.

`MAINTENANCE_MODE=true` и `ORDER_STATUS_NOTIFICATIONS_ENABLED!=true` останавливают worker и provider до POST. Некорректный HTTPS `APP_ORIGIN` останавливает claim без расходования попыток.

## Независимые разрешения и граница запуска

Общий `ORDER_STATUS_NOTIFICATIONS_ENABLED` остаётся master kill switch. Его одного недостаточно: `TELEGRAM_ORDER_STATUS_NOTIFICATIONS_ENABLED` и `MAX_ORDER_STATUS_NOTIFICATIONS_ENABLED` разрешают соответствующий канал только при точном значении `true`; по умолчанию оба выключены. Токен не является разрешением на отправку.

Для каждого канала обязателен собственный `*_ORDER_STATUS_NOTIFICATIONS_NOT_BEFORE`: корректный UTC timestamp `YYYY-MM-DDTHH:mm:ssZ` или с тремя цифрами миллисекунд, не позднее текущего времени. Пустая, некорректная или будущая граница блокирует канал. **И заказ, и запись доставки должны быть созданы не раньше этой границы.** Это также блокирует повторную постановку исторического события старого заказа с новым временем доставки. Границу выбирают в согласованный момент запуска, после проверки backlog и до создания нового canary-заказа; впоследствии её не сдвигают назад. Перезапуск и смена OFF/ON не сбрасывают границу, статусы или попытки.

Один SQL scope применяется к claim, изоляции неоднозначных результатов, исчерпанным попыткам, проверке заказа, `superseded`, ошибкам и ручному retry. Выключенный канал, старые строки и другие canary-заказы не меняются даже при обслуживании очереди. Обработка повторно проверяет scope после claim; непосредственно перед HTTP проверяются разрешения, UUID заказа и времена заказа/доставки. Подтверждённое принятие API сохраняется для той же попытки даже если после POST разрешение выключили: это история принятия, а не новая отправка.

`TELEGRAM_ORDER_STATUS_NOTIFICATIONS_MODE` по умолчанию `canary`; поддерживаются только `canary` и `live`. Canary требует валидный `TELEGRAM_ORDER_STATUS_NOTIFICATIONS_CANARY_ORDER_ID` (UUID v1–v5). Без ID, при ошибочном ID или неизвестном mode отправка закрыта. Canary разрешает только Telegram-событие `ready` для этого заказа, включая обслуживание очереди и ручной retry; `cancelled` не захватывается, не отправляется и не возвращается ручным retry; MAX в этом режиме заблокирован даже при ошибочно выставленном разрешении. Unique key события `ready` сохраняет ограничение одной постановки. Режим `live` явно снимает ограничения одного заказа и события `ready`, сохраняя обычную доставку `ready/cancelled`, границу запуска и остальные проверки.

Старые строки остаются в очереди и сохраняют историю и unique key. Их возраст сам по себе не служит разрешением или запретом — действует явная граница. `sent` и `superseded` не захватываются и не возвращаются ручным retry; сроки `available_at` и `updated_at` не могут обойти `created_at`. Очистка таблицы и сброс статусов не являются способом запуска.

## Согласованный запуск только Telegram

1. После отдельного согласования выпустить код с master OFF и обоими разрешениями OFF. Производственные миграции или изменения очереди для этого PR не нужны.
2. После отдельного согласования адресно перевести две зафиксированные старые Telegram-записи в `superseded` с аудитом: точные ID перечитываются в Timeweb; одна транзакция проверяет `provider=telegram`, `status=pending`, `attempts=0`, отсутствие lease, `sent_at` и provider message ID, а также ожидаемое количество **2**. При несовпадении условий — rollback. Ничего не удалять, попытки не обнулять; MAX не изменять.
3. Вставить токен непосредственно в локальные переменные приложения Timeweb. Секрет не передавать в чат, команды, Git, build args или `NEXT_PUBLIC_*`; не читать и не снимать форму с введённым значением. Применение env/restart согласуются отдельно. При master OFF проверить только наличие токена, `getMe`, актуальную identity и Telegram backlog. Старый transport-preflight script не проверяет новые разрешения/canary/границы и не является разрешением на запуск worker.
4. Зафиксировать UTC границу Telegram и создать один новый реальный заказ разрешённого покупателя **после** неё. `is_test=true` исключён из outbox. Указать его UUID, mode `canary`, разрешение Telegram ON, MAX OFF; после отдельного разрешения включить master и перезапустить приложение. Не вызывать общий batch вручную и не сбрасывать очередь.
5. Через обычный статус заказа проверить «Готов»: одна eligible Telegram-строка, одно сообщение с номером и HTTPS-кнопкой, `sent`, provider acceptance и отсутствие повтора после нескольких циклов (10 секунд). Старые строки и прочие заказы не обрабатываются. Проверка «Отменён» требует отдельного согласованного бизнес-сценария; не отменять оплаченный заказ только ради теста.
6. При ошибке выключить master и остановить worker перезапуском, затем проверять результат; не возвращать неоднозначную попытку в очередь. Переход в `live` — отдельное разрешение после сверки оставшихся eligible Telegram-записей; MAX разрешение остаётся OFF.

Зафиксированный read-only срез Timeweb от 12 октября 2026: две Telegram `pending` от `2026-09-11T17:41:57.750Z` и `2026-10-05T18:58:07.302Z`, событие `ready`, попыток 0, lease и признаки отправки отсутствуют, оба заказа `handed_out`. Это запись состояния для будущего адресного supersede, **не выполненная операция**. Полные order/customer/chat/identity ID не публикуются.

## Операционный экран

Маршрут `/admin/notifications`, роли только `owner/admin`, включая существующего legacy admin. Проверка выполняется на сервере перед чтением данных и перед действием. Менеджеру без глобального доступа экран недоступен. Общая навигация и авторизация принадлежат родительской задаче.

Экран показывает счётчики всех шести статусов по провайдерам, наступивший срок, зависшие попытки, ожидание более суток, последнее принятие и 50 последних записей с фильтром внимания. Конфигурация отображается только булевыми признаками. Нет имён, телефонов, chat ID, provider payload и message ID. `sent` означает принятие API, не подтверждение прочтения. Ошибка чтения/отсутствующая схема не маскируется нулевыми счётчиками.

Единственный ручной повтор: **первая** попытка, `permanent_failure` только из-за `app_origin_not_configured`, `telegram_not_configured`, `max_not_configured` или `telegram_recipient_unverified`; `sent_at`, `provider_message_id`, `locked_at` отсутствуют; срок наступил; конфигурация теперь исправна, отправка включена, maintenance выключен; заказ и identity актуальны. Для Telegram обязателен корректный `metadata.telegramBotUserId`, включая повтор после обычного входа, обогатившего старую identity. Требуется отдельный checkbox подтверждения одной записи. Условный UPDATE повторно проверяет всё в БД и атомарно пишет `audit_logs`, не обнуляя попытки. Действие только возвращает запись в очередь, не вызывает provider. Остальные ошибки, старые неоднозначные результаты и массовый повтор недоступны.

Экран не включает доставку, не меняет токены, не создаёт кампании и не отправляет тестовые сообщения. При открытии страницы выполняются только чтения.

## Безопасное включение

По умолчанию отправка выключена:

```dotenv
ORDER_STATUS_NOTIFICATIONS_ENABLED=false
TELEGRAM_ORDER_STATUS_NOTIFICATIONS_ENABLED=false
MAX_ORDER_STATUS_NOTIFICATIONS_ENABLED=false
TELEGRAM_ORDER_STATUS_NOTIFICATIONS_NOT_BEFORE=
MAX_ORDER_STATUS_NOTIFICATIONS_NOT_BEFORE=
TELEGRAM_ORDER_STATUS_NOTIFICATIONS_MODE=canary
TELEGRAM_ORDER_STATUS_NOTIFICATIONS_CANARY_ORDER_ID=
TELEGRAM_BOT_TOKEN=
```

`TELEGRAM_BOT_TOKEN` — отдельный BotFather token. Нельзя подставлять вместо него `TELEGRAM_OIDC_CLIENT_SECRET`. Для MAX используется существующий server-only `MAX_BOT_TOKEN`.

Подтверждённое родительской задачей состояние production через read-only Timeweb API на 2026-09-08: `ORDER_STATUS_NOTIFICATIONS_ENABLED=false`, `TELEGRAM_BOT_TOKEN` отсутствует, `MAX_BOT_TOKEN` задан, `TELEGRAM_OIDC_CLIENT_ID` задан. Значения секретов не запрашивались; окружение не менялось. Наличие MAX token и OIDC client ID не подтверждает возможность доставки. Telegram Bot Token и обогащение старых адресатов подписанным ID при обычном входе остаются условиями активации.

**Важно:** migration не создаёт записи для событий до её установки, но trigger продолжает ставить новые события в очередь при выключенном worker. Включение может отправить накопленные ранее `pending/retry`, включая старые отмены. Нет автоматического TTL или даты начала доставки. До включения требуется согласованный разбор накопленной очереди, не автоматический исторический backfill и не массовый retry.

Полный список шагов включения, остающихся рисков и архитектура согласий: [аудит сентября 2026](audit-2026-09-notifications.md). Migration, смена окружения, DB writes, реальные пробные отправки и deploy требуют отдельного разрешения; в этой задаче они не выполнялись.

## Проверка перед включением и адресный smoke-test

Команда `npm run telegram:notifications:preflight` не меняет базу и конфигурацию. Она вызывает Bot API `getMe`, читает агрегаты очереди отдельно для Telegram и MAX и при заданном `TELEGRAM_SAFE_TEST_CHAT_ID` проверяет, что этот ID связан ровно с одной записью Telegram Login в KARIMOFF. Она сообщает только наличие `MAX_BOT_TOKEN`, не проверяя доставку через MAX. В выводе нет токенов, chat ID, номеров заказов или персональных данных.

`queueAndConfigPreflightPassed` будет `true` только при выключенном worker, корректной HTTPS-ссылке, доступном Telegram Bot API, настроенном MAX-токене, доступной схеме и отсутствии `pending`, `retry` и `processing` в обеих очередях и зависших блокировок. Если есть backlog, в том числе старше 24 часов, команда только покажет счётчики и оставит включение заблокированным; исключать старые записи можно только отдельным согласованным действием. Успешный preflight не подтверждает доставку через MAX или право Telegram-бота писать конкретному пользователю. Перед включением нужны отдельные проверки MAX и Telegram-адресата.

Для одноразового smoke-test нужны временные переменные оператора `TELEGRAM_SAFE_TEST_CHAT_ID` (ID заранее разрешённого тестового аккаунта) и `TELEGRAM_EXPECTED_BOT_USERNAME` (ожидаемый username бота), кроме обычных `TELEGRAM_BOT_TOKEN`, read-only `DATABASE_URL` и `APP_ORIGIN`. Telegram Login уже запрашивает разрешение `write`, но `getMe` проверяет только токен и самого бота, не право писать конкретному пользователю. Только `sendMessage` конкретному тестовому чату проверяет это право; отказ `400/403` показывается как отказ адресата/разрешения, а сетевой/серверный неизвестный исход не повторяется.

Без `--send-once` команда никогда не отправляет сообщение. Режим `--send-once` дополнительно требует TTY-подтверждение по последним четырём цифрам ID, проверяет единственную связь ID с аккаунтом и блокируется, если worker включён, активен maintenance или username бота не совпадает. Он отправляет ровно одно явное тестовое сообщение, не пишет в outbox и не повторяет запрос при неизвестном исходе.

```sh
npm run telegram:notifications:preflight
npm run telegram:notifications:preflight -- --send-once
```

Запуск `--send-once` требует отдельного разрешения владельца на одно реальное сообщение. Эта задача его не запускала. Секреты не сохраняются в checkout.

### Снимок production Timeweb от 2026-10-10

Проверка выполнена read-only в `karimoff-production`; ни production env, ни очередь не изменялись.

- Bot API `getMe` подтвердил доступность `@Karimoff_food_bot`. Сообщения не отправлялись.
- В runtime заданы `TELEGRAM_OIDC_CLIENT_ID`, `TELEGRAM_OIDC_CLIENT_SECRET`, `DATABASE_URL` и `APP_ORIGIN`; `APP_ORIGIN` ведёт на HTTPS `karimoff.site`, ссылка кабинета — `/profile/orders`.
- `TELEGRAM_BOT_TOKEN` отсутствует, `ORDER_STATUS_NOTIFICATIONS_ENABLED` не задан и worker выключен. `MAINTENANCE_MODE` выключен. `TELEGRAM_EXPECTED_BOT_USERNAME` не задан; он нужен операторскому preflight, но не является production-флагом worker.
- В Telegram-части очереди 2 `pending` события `ready`, оба уже доступны к отправке; возраст самой старой записи — около 693 часов. `processing`, `retry` и `permanent_failure` — 0; у этих двух записей `last_error_code` не задан. Включать worker до разбора этих старых событий нельзя.
- Указанный тестовый Telegram ID не найден среди связей `metadata.telegramBotUserId` (0 точных совпадений). Всего в БД 3 Telegram identity, из них у 1 записан Bot user ID.
- Право писать этому получателю не подтверждено. `getMe` проверяет бота, а не адресата; отдельное тестовое `sendMessage` не выполнялось. Последующая read-only попытка `getChat` не дала диагностического ответа после того, как буфер обмена перестал содержать token-shaped значение.

Перед запуском нужно связать аккаунт получателя через Telegram Login и телефон KARIMOFF, отдельно разобрать или пометить `superseded` обе старые записи, затем выполнить согласованный одноразовый тест. Только после этого, с отдельным разрешением, добавлять production `TELEGRAM_BOT_TOKEN` как secret и включать `ORDER_STATUS_NOTIFICATIONS_ENABLED=true`.
