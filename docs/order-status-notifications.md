# Уведомления о заказах

KARIMOFF ставит транзакционное уведомление в очередь только при переходе canonical kitchen status в `ready` или `cancelled`. Тестовые заказы исключены. Очередь не меняет заказ, выручку, склад, KDS или фискальные документы.

## Доставка

- Telegram: официальный Bot API `sendMessage`. Login Library запрашивает scope `write`; для OIDC документация отдельно называет `telegram:bot_access`. Запрошенное разрешение не равно сохранённому доказательству его выдачи и не является согласием на рекламу.
- Telegram использует **только** `identity.metadata.telegramBotUserId`: parent/auth сохраняет это строковое поле из положительного safe-integer `claims.id` после проверки подписи. `provider_user_id=claims.sub` остаётся ключом входа и никогда не используется как fallback `chat_id`. Worker повторно проверяет формат и безопасный диапазон ID; отсутствие/некорректное значение останавливает доставку с `telegram_recipient_unverified`.
- Старые identities получат поле при следующем обычном входе в Telegram. Принудительный relink и DB migration не требуются. `botAccessRequested` означает только запрошенный доступ; отказ провайдера остаётся действующим ограничением доставки.
- MAX: официальный `POST https://platform-api2.max.ru/messages?user_id=...`, bot token передаётся только в заголовке `Authorization`.
- MAX user ID берётся из подписанных MAX Mini App claims, нормализуется как положительный canonical ID в диапазоне `int64` и сохраняется в существующей `user_identities.provider_user_id`. Привязка к KARIMOFF аккаунту разрешается по этой identity; профильное имя, username и фотография не используются для объединения аккаунтов.
- MAX Login сам по себе не доказывает, что бот может писать пользователю. Только подписанные заголовком `X-Max-Bot-Api-Secret` события `bot_started`, `bot_stopped` и `dialog_removed` обновляют минимальное состояние диалога. Worker пропускает MAX запись, если нет активного `bot_started`; перед POST состояние проверяется ещё раз.
- Обе ссылки ведут только на HTTPS origin из `APP_ORIGIN` + `/profile/orders`; credentials, query, fragment, session ID, order token и PII в URL не передаются. Следование HTTP redirect при POST запрещено.

Официальные разделы:

- https://core.telegram.org/bots/telegram-login
- https://core.telegram.org/bots/api#sendmessage
- https://dev.max.ru/docs-api/methods/POST/messages

## Надёжность

`order_notification_deliveries` имеет unique constraint `(order_id, identity_id, event_type)`: это защита от повторной постановки, **не exactly-once доставка**. Worker забирает только `pending/retry` с числом попыток меньше восьми через `FOR UPDATE SKIP LOCKED`. Перед POST проверяются текущий статус заказа, `is_test=false`, действующая identity и её принадлежность тому же покупателю. Обновления результата ограничены текущей попыткой и состоянием.

Telegram повторяет 429 и явные 5xx с ограниченным backoff. MAX повторяет только 429 с учётом `Retry-After` в секундах или HTTP-date; без корректного заголовка используется 30 секунд. HTTP 5xx, timeout, потеря соединения и неполный 2xx для MAX считаются неизвестным результатом и не повторяются, чтобы не отправить дубль после принятия API. Для обеих платформ повторы останавливаются после восьмой попытки.

MAX API ограничивает доставку двумя сообщениями в секунду в один диалог. Worker сериализует MAX события одного получателя не чаще одного раза в секунду; другие адресаты продолжают обрабатываться из общей очереди.

Сетевой обрыв, timeout/408, неполный успешный ответ и lease старше пяти минут означают неизвестный результат. Такие записи переходят в `permanent_failure` с безопасным кодом и **не отправляются повторно автоматически**. Старые `retry` после network/unknown failures также изолируются. Это сознательный выбор против дублей с возможной потерей доставки до ручной проверки, не гарантия доставки.

Успех требует `result.message_id` у Telegram или `message.body.mid` у MAX. Если провайдер принял сообщение, а сохранение результата упало, запись не переводится в `retry`; истёкший lease будет изолирован. Позднее подтверждение той же попытки может зафиксировать `sent`. Ошибки scheduler перехватываются; в журнал не попадают исходные исключения, provider payload, bot token или телефон.

`MAINTENANCE_MODE=true` и `ORDER_STATUS_NOTIFICATIONS_ENABLED!=true` останавливают worker и provider до POST. Некорректный HTTPS `APP_ORIGIN` останавливает claim без расходования попыток.

## Операционный экран

Маршрут `/admin/notifications`, роли только `owner/admin`, включая существующего legacy admin. Проверка выполняется на сервере перед чтением данных и перед действием. Менеджеру без глобального доступа экран недоступен. Общая навигация и авторизация принадлежат родительской задаче.

Экран показывает счётчики всех шести статусов по провайдерам, наступивший срок, зависшие попытки, ожидание более суток, последнее принятие и 50 последних записей с фильтром внимания. Конфигурация отображается только булевыми признаками. Нет имён, телефонов, chat ID, provider payload и message ID. `sent` означает принятие API, не подтверждение прочтения. Ошибка чтения/отсутствующая схема не маскируется нулевыми счётчиками.

Единственный ручной повтор: **первая** попытка, `permanent_failure` только из-за `app_origin_not_configured`, `telegram_not_configured`, `max_not_configured` или `telegram_recipient_unverified`; `sent_at`, `provider_message_id`, `locked_at` отсутствуют; срок наступил; конфигурация теперь исправна, отправка включена, maintenance выключен; заказ и identity актуальны. Для Telegram обязателен корректный `metadata.telegramBotUserId`, включая повтор после обычного входа, обогатившего старую identity. Требуется отдельный checkbox подтверждения одной записи. Условный UPDATE повторно проверяет всё в БД и атомарно пишет `audit_logs`, не обнуляя попытки. Действие только возвращает запись в очередь, не вызывает provider. Остальные ошибки, старые неоднозначные результаты и массовый повтор недоступны.

Экран не включает доставку, не меняет токены, не создаёт кампании и не отправляет тестовые сообщения. При открытии страницы выполняются только чтения. Для проверки MAX webhook добавлен признак наличия секрета; он не подтверждает, что подписка реально зарегистрирована в MAX.

## Безопасное включение

По умолчанию отправка выключена:

```dotenv
ORDER_STATUS_NOTIFICATIONS_ENABLED=false
TELEGRAM_BOT_TOKEN=
```

`TELEGRAM_BOT_TOKEN` — отдельный BotFather token. Нельзя подставлять вместо него `TELEGRAM_OIDC_CLIENT_SECRET`. Для MAX используется существующий server-only `MAX_BOT_TOKEN`.

Историческая проверка production через read-only Timeweb API от 2026-09-08 показывала `ORDER_STATUS_NOTIFICATIONS_ENABLED=false` и наличие `MAX_BOT_TOKEN`. Текущая production-конфигурация в этой задаче не подключена и не подтверждена. Локально отсутствуют `DATABASE_URL`, `APP_ORIGIN`, `MAX_BOT_TOKEN` и `ORDER_STATUS_NOTIFICATIONS_ENABLED`; секреты не раскрывались.

**Важно:** migration не создаёт записи для событий до её установки, но trigger продолжает ставить новые события в очередь при выключенном worker. Включение может отправить накопленные ранее `pending/retry`, включая старые отмены. Нет автоматического TTL или даты начала доставки. До включения требуется согласованный разбор накопленной очереди, не автоматический исторический backfill и не массовый retry.

Полный MAX preflight и безопасный canary описаны в [плане MAX уведомлений](max-order-notifications.md). Migration, смена окружения, DB writes, реальные пробные отправки и deploy требуют отдельного разрешения; в этой задаче они не выполнялись.
