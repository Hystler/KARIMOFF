# Оплата на физическом Эвотор и готовность Яндекс Еды

Проверено 2026-09-09. Исследование исходников только на чтение и текущих официальных страниц developer.evotor.ru / eda-vendor. Запросов к рабочим API, платежей, установки приложений, изменения окружения и развёртывания не было. Ниже будущие действия, а не выполненная настройка.

## Решение кратко

Текущая интеграция импортирует чеки, но не инициирует оплату. Для POS в браузере нужны либо собственный APK на физической кассе и push + SDK, либо заказы готового «Мобильного кассира». Это разные интеграции с разными ключами. Ни один вариант не превращает обычный REST-токен чтения в команду списания с карты.

Предварительный выбор: APK + SDK для управляемого сценария «выбранный заказ -> выбранная касса -> оплата -> проверенный результат»; «Мобильный кассир» для сценария, где сотрудник открывает поступивший заказ в готовом приложении. Окончательный выбор блокируют модель кассы, версия EvotorPOS и способ подключения эквайринга; их уточняет родительская задача.

У Яндекс Еды **есть документированные методы истории за 180 дней**. Возможен отдельный аналитический импорт, но доступ KARIMOFF и условия подключения должен подтвердить провайдер. Не путать историю с входящим операционным API ресторана.

## Проверенная конфигурация физического терминала

Проверено 2026-09-21 локальным диагностическим APK без открытия чека и запуска оплаты:

- устройство `p10bio`, Android 11 (API 30), Evotor POS `8.23.0.1-863`;
- эквайринг Сбербанк `1.105.549`, UPOS Init Loader `1.0.12`, EvoXcPaySystem `3.1.5-114`, KkmDriver `5.5.2-270`;
- Evotor публикует только встроенные исполнители `Наличные` и `Банковская карта`;
- единственный сервис драйвера банковских терминалов — `ru.evotor.drivers.kozenpaysystem.PaySystemService` (`PAYSYSTEM`);
- у встроенной безналичной системы зарегистрированы три аккаунта с локальными `accountId` `0`, `1`, `2`; все три имеют одинаковое описание `Виртуальное устройство`;
- read-only методы драйвера для всех трех экземпляров возвращают пустое название банка и одинаковый номер терминала `1`, поэтому программно различить их по опубликованным метаданным нельзя.

В интерфейсе оборудования те же три устройства показаны в порядке: автономный пинпад, интегрированная платёжная система, UPOS; UPOS выбран по умолчанию. Отсюда следует рабочая гипотеза `accountId 2 = UPOS`, но опубликованный API этого напрямую не подтверждает. До контролируемого пилота нельзя считать эту привязку доказанной или использовать её для автоматического списания.

## Постоянный канал KARIMOFF -> Эвотор

Подготовлен независимый от ноутбука HTTPS-канал: сайт ставит задание предпросмотра на сервере KARIMOFF, а APK на кассе забирает его исходящим HTTPS-запросом. Ноутбук, локальный IP и ADB после установки APK не участвуют. Кассе нужен интернет, а постоянно работающей частью остаются уже существующий сервер `karimoff.site` и его база данных.

Первичная привязка выполняется одноразовым восьмизначным кодом из админки. В APK сохраняется отдельный случайный bearer-токен устройства; сервер хранит только HMAC-отпечаток. Код действует 10 минут и после использования закрывается. Очередь изолирована по устройству, задания истекают через 30 минут и подтверждаются тем же устройством.

Контур намеренно ограничен предпросмотром заказа: он не открывает чек, не обращается к платёжному исполнителю, не печатает и не меняет статус заказа. По умолчанию отключены и сам канал (`EVOTOR_TERMINAL_BRIDGE_ENABLED=false`), и отправка нетестовых заказов (`EVOTOR_TERMINAL_ALLOW_LIVE_PREVIEW=false`). Миграция, серверные переменные, развёртывание и установка новой APK-версии выполняются отдельным контролируемым этапом.

## Evotor: поддерживаемые пути

### A. Собственный APK + push + SDK

Архитектура: POS -> сервер KARIMOFF с сохранённой попыткой -> адресный push -> наш APK получает заказ с сервера -> SDK кассы -> установленный исполнитель оплаты -> банк / фискализация -> результат на сервер и сверка чека.

- Push: `POST https://api.evotor.ru/api/apps/{application_id}/devices/{device_uuid}/push-notifications`; ответ `202` и ID задачи. `ACCEPTED`, `RUNNING`, `COMPLETED`, `FAILED` относятся к доставке/обработке уведомления, не являются банковским результатом. Проверка задачи: `GET /api/apps/{application_id}/push-notifications/{push-id}`. [Контракт push](https://developer.evotor.ru/docs/rest_api_post_apps_app_devices_device_push_notifications.html).
- Ограничения адресного push: 1000 запросов/час на приложение и устройство, `payload` менее 1900 символов, срок действия `active_until`. Рекомендация: передавать ID попытки, не весь чек и не персональные данные. [Руководство](https://developer.evotor.ru/docs/rest_push_notifications_guide.html).
- На сервере нужен **ключ издателя** с правом передачи push, создаваемый во вкладке «Ключ доступа издателя» -> «Права доступа». Это не сохранённый application token пользователя; последний оставить для чтения документов. [Авторизация издателя](https://developer.evotor.ru/docs/rest_publisher_access_token.html).
- APK: `PushNotificationReceiver`, permission `ru.evotor.pushnotifications.PUSH_RECEIVE`; receiver защищён `ru.evotor.pushnotifications.PUSH_SENDER`, action `ru.evotor.pushnotifications.PUSH_RECEIVED_EVENT`. [Приём push](https://developer.evotor.ru/docs/doc_java_pushnotifications.html). В manifest нужен `app_uuid` из портала. [Manifest](https://developer.evotor.ru/docs/doc_java_app_manifest.html).
- Продажа: `OpenSellReceiptCommand`, затем `NavigationApi.createIntentForSellReceiptPayment()`; альтернативно передать открытый чек выбранному `PaymentPerformer` / `PaymentDelegator` через `SellApi.moveCurrentReceiptDraftToPaymentStage()`. Это запуск процесса, не доказательство его завершения. [Открытие чека](https://developer.evotor.ru/docs/doc_java_receipt_creation.html), [оплата из приложения](https://developer.evotor.ru/docs/doc_java_in_app_receipt_payment.html).
- Нельзя затирать чужой открытый чек. Документация описывает защиту от непустого другого чека начиная с EvotorPOS 8.11.0 и integration-library 0.6.03; учитывать фактические версии, занятость и восстановление незавершённого чека. [Ошибки открытия](https://developer.evotor.ru/docs/doc_java_receipt_creation.html).
- Для сверки доступны `ReceiptApi.getReceipt(context, uuid)` и платежи чека. Приложение должно сохранять связь попытки с реальным UUID кассового чека; исчезновение текущего открытого чека само по себе не успех. [Чтение чека](https://developer.evotor.ru/docs/doc_java_get_receipt.html).
- Права роли кассира и ограничения компонентов задаются отдельно: `CASH_OPERATIONS_SELL`, для возвратов `CASH_OPERATIONS_PAYBACK`, metadata `ru.evotor.launcher.GRANTS`. Это не REST scopes и не Android permissions. [Права приложения](https://developer.evotor.ru/docs/doc_app_grants.html).

Ручная установка для будущего пилота: приложение с APK на портале -> загрузить APK с корректным package/app UUID -> тестовая версия и аккаунт тестировщика -> установить на выбранную кассу. Для установки из магазина режим разработчика выключен; ADB является отдельным способом с включённым режимом разработчика. Текущая облачная установка без APK недостаточна. [Официальная установка](https://developer.evotor.ru/docs/doc_app_installation.html). Публикация и установка требуют отдельного разрешения пользователя.

### B. Облачные заказы «Мобильного кассира»

`POST https://mobcashier.evotor.ru/api/v1/orders/create` передаёт **предварительный чек** в раздел «Заказы» приложения на кассе или смартфоне. Сотрудник принимает оплату доступным способом, после чего выполняется фискализация. Это не API немедленного списания с карты. Есть `receipt_uuid`, позиции, `cashier_uuid`, печать, контакт покупателя, `editable`, `extra`, `callback`; документированного выбора `device_uuid` в create нет, `cashier_uuid` определяет видимость сотруднику. Маршрутизацию строго на одну кассу нужно согласовать. [Создание заказа](https://developer.evotor.ru/docs/api_v1_orders_create.html).

Подключение: написать **mk@evotor.ru** сценарий, организацию, ИНН, телефон ЛК Эвотор и контактный email; получить идентификатор интеграции. Затем серверный `POST /api/v1/authorize/integration` возвращает `user_id`, `token`, `android_id`. Последующие запросы используют `Authorization: Bearer` и `AndroidId`. Это отдельная авторизация только Мобильного кассира. [Доступ и токен](https://developer.evotor.ru/docs/api_v1_authorize_integration.html). Значения секретов не передавать в чат.

Готовое приложение нужно установить и настроить на выбранном устройстве. Смартфонный App-to-App вариант использует Android `RemoteCashierSDK`, а не JavaScript браузера; нужны приложение на смартфоне и касса для фискализации. Документация SDK указывает обновление токена раз в сутки и допускает офлайн-очередь. Режим без кассы не фискализирует. Это отдельная альтернатива, не требование облачного create для кассового приложения. [SDK и требования](https://developer.evotor.ru/docs/mc_integration.html).

Критические ограничения:

- `200` create подтверждает приём запроса; `409` документирован для уже фискализированного `receipt_uuid`. Это повод сверить чек, а не создать новый UUID и повторно списать. Поведение повтора ещё не оплаченного заказа / изменения его содержимого нужно уточнить. [Коды create](https://developer.evotor.ru/docs/api_v1_orders_create.html).
- `GET /api/v1/orders/get` имеет `page_size`, `page_number`, `since`, `until`, `cashier_uuid`, `shopUuid`. В опубликованной схеме нет документированного финального статуса оплаты/фискализации. Отсутствие заказа в списке не подтверждает оплату. [Список заказов](https://developer.evotor.ru/docs/api_v1_orders_get.html).
- Callback содержит `fiscalization.fiscalized`, фискальные данные, `receipt_uuid`, сумму и платежи, но **доступен только для мобильного приложения смартфона**. Его страница требует HTTPS без авторизации, тогда как create описывает `callback.auth`. Это противоречие и блокер доверенного callback; не открывать незащищённый endpoint, который выставляет `paid`. Нужны ответ провайдера и независимая серверная сверка. [Callback](https://developer.evotor.ru/docs/api_v3_asc_transfer.html).

### Банковский терминал не равен кассе

Фискальная касса Эвотор и банковский пинпад выполняют разные операции. Для связанного эквайринга на кассе должен быть совместимый платёжный исполнитель/драйвер; официальный SDK описывает USB и виртуальные сетевые/Bluetooth-драйверы. Название банка или наличие внешнего терминала само по себе совместимость не доказывает. [SDK пинпадов](https://developer.evotor.ru/docs/doc_drivers_pinpads.html).

Если сумма вводится вручную на автономном банковском терминале, Эвотор не получает автоматически доказательство банковского списания. Поле «Внешний терминал» / `ELECTRON` не является таким доказательством. До подтверждения связанного режима считать это ручным процессом с отдельной сверкой; автоматический bank API не входит в подтверждённый объём. Нельзя брать деньги повторно за уже оплаченный онлайн-заказ: фискализация предоплаты требует отдельного согласованного сценария.

## Контракт KARIMOFF для реализации

Это проектные требования, не обещания API провайдеров:

1. Отдельные сущности платёжной попытки, доставки команды и фискального результата. Не заменять их одним `paid`. Например: `pending`, `awaiting_customer`, `payment_confirmed`, `fiscalization_pending`, `completed`, `failed`, `unknown`.
2. До отправки сохранять неизменяемый снимок состава/суммы/скидок/налогов, order ID, attempt ID, целевые кассу/точку. Уникальная активная попытка на заказ; блокировка одновременной работы с кассой. Все суммы сверять точно, не по приблизительному совпадению времени.
3. Outbox и журнал обработки на APK: повтор push/нажатия/перезапуска возвращает состояние той же попытки, а не создаёт новую продажу. У Мобильного кассира сохранять один `receipt_uuid`; гарантии exactly-once до подтверждения провайдера не заявлять.
4. Получать подтверждение от доверенного терминального компонента и сверять закрытый фискальный чек через существующее чтение. Проверять UUID, точку, устройство, сумму, вид операции и фискальные реквизиты. Договориться и проверить на пилоте соответствие UUID Мобильного кассира идентификатору документа Cloud v2; не считать их автоматически одинаковыми.
5. Подписанный/аутентифицированный результат, защита от повторов, дедупликация входящих событий и авторизация устройства. Для неподписанного provider callback допустимо только поставить сверку в очередь. Задержка облака, таймаут и потерянный callback дают `unknown/pending`, не разрешение повторного списания.
6. Банковская оплата успешна, фискализация ошиблась: заблокировать повтор платежа, выделить восстановление/ручную проверку. Возврат денег, отмена заказа и возвратный чек являются отдельными операциями.
7. Связать проверенный чек с заказом для единого учёта. Не создавать вторую продажу и повторное складское списание при импорте чека.

## Яндекс Еда: история и операционные заказы

**История:** сервер Яндекса `https://dc-partner.eda.yandex.net`. Авторизация `POST /oauth2/token`, form-urlencoded `client_id`, `client_secret`; Bearer, `scope=vendor_management` в примере ответа, обновление по фактическому `expires_in`, не по числу из примера. Получение credentials не является обычным входом в Яндекс ID. [Базовый адрес](https://yandex.ru/dev/eda-vendor/doc/ru/ref/Vendor-Management-Integration-API/), [авторизация](https://yandex.ru/dev/eda-vendor/doc/ru/ref/Vendor-Management-Integration-API/BlocksAuth).

| Метод | Данные и ограничения |
| --- | --- |
| `POST /v1/orders-history` | Последние 180 дней, до 1000 заказов в ответе; `pagination.limit/offset`, даты создания `from/to`, `origin_ids` с типом доставки, сервис, статусы NEW/CANCELLED/DELIVERED. Возвращает `eats_id`, `order_id`, `created_at`, ресторан, сервис, статус, `items_cost`, причину отмены. |
| `POST /v1/get-orders-details` | До 100 `eats_ids` за запрос, также 180 дней. Состав: ID/название, количество, цена, вес, единицы, модификаторы; `not_found_eats_ids` для ненайденных/недоступных заказов. `price` уже включает опции, `original_price` их не включает: это не автоматически «цена до скидки». |

Источники: [история](https://yandex.ru/dev/eda-vendor/doc/ru/ref/Vendor-Management-Integration-API/partner.orders.history.post), [детали](https://yandex.ru/dev/eda-vendor/doc/ru/ref/Vendor-Management-Integration-API/partner.integration.v1.get.orders.details.post). Эти POST семантически читают данные; в этой задаче они не вызывались.

Из этих данных можно рассчитать заказы, отмены, оборот по `items_cost`, средний заказ, продажи позиций/модификаторов и динамику по точкам/датам. `items_cost` учитывает партнёрские скидки и исключает доставку; это **не подтверждённая выплата после комиссии**. В проверенных контрактах нет обещания истории старше 180 дней, комиссий, банковских выплат, рекламных показов/конверсий, клиентских когорт или полного финансового отчёта. Запросить отдельную официальную выгрузку/контракт, не придумывать analytics endpoint.

**Операционные заказы:** Яндекс обращается к серверу партнёра; партнёр реализует приём, изменение, отмену, выдачу заказа/статуса, меню/остатки и ресторанные данные. Нельзя обращаться к своему будущему `GET /order/{order_id}` как к облачной истории Яндекса. [Модель взаимодействия](https://yandex.ru/dev/eda-vendor/doc/ru/ref/), [методы и тестовые коллекции](https://yandex.ru/dev/eda-vendor/doc/ru/collections).

### Ручное подключение и вопросы Яндексу

В рассмотренных eda-vendor страницах **не опубликован полный self-service onboarding**, адрес для выдачи credentials или гарантия выдачи только аналитического доступа. Не выдумывать письмо/форму регистрации разработчика. Документация направляет в кабинет ресторана, где есть поддержка. [О сервисе](https://yandex.ru/dev/eda-vendor/doc/ru/).

Практический запрос владельца через поддержку кабинета / действующего менеджера (это рекомендуемый следующий шаг, не документированный регламент выдачи):

1. Попросить подключить KARIMOFF как собственную интеграцию ресторана; указать точки, действующую учётную систему и желаемый режим **только истории, без переключения приёма заказов**.
2. Запросить credentials Vendor Management, разрешение на оба метода истории, список доступных `origin_id` + `delivery_type`, ограничения частоты и тестовый доступ. Уточнить, доступна ли история до подключения и при существующем стороннем интеграторе.
3. Получить письменное подтверждение, можно ли оставить действующий приём заказов; какие договорные/технические проверки нужны; кто назначает идентификаторы. Не обещать параллельную работу двух операционных интеграций.
4. Для дальнейшего приёма заказов согласовать HTTPS base URL, авторизацию Яндекс -> KARIMOFF, обязательные методы, сопоставление меню, тесты по официальной коллекции и отдельную дату переключения.
5. Для старой истории, комиссий и выплат запросить официальный способ выгрузки и глубину хранения. Отсутствующие/недоступные записи отражать как неполноту данных, не нули.

Рекомендуемый аналитический импорт: небольшие фиксированные окна с offset-пагинацией -> детали пачками <=100 -> upsert по провайдеру и `eats_id` -> периодическая перепроверка недавних окон и незавершённых заказов. Фильтр по дате создания не является курсором обновлений. Хранить историю локально, не запускать кухню/склад при backfill и исключить дубли с фискальными продажами Эвотор.

## Блокеры и передача в разработку

| Что требуется | Кто / критерий снятия блокера |
| --- | --- |
| Модель Эвотор, EvotorPOS/Android, банк, модель пинпада, связанный или ручной режим | Пользователь; родительская задача уже ожидает модель. Дополнительно уточнить, откуда работает браузер POS и допустимо ли открывать заказ на кассе вручную. |
| APK или Мобильный кассир | Владелец выбирает после демонстрации предполагаемого процесса. Уточнить лицензии/подписку, доступность приложения для модели и тестовую кассу. |
| Достоверный итог Мобильного кассира именно на кассе | Evotor: доступность callback без смартфона, его auth/повторы, способ опроса результата, связь UUID, повтор create до оплаты, адресация кассы. До ответа нет готовности к автоматическому `paid`. |
| Фискальный состав | Владелец/ответственный за кассу подтверждает НДС, признаки расчёта, скидки, маркировку, печать и контакт покупателя; не копировать ставки из примеров. |
| Яндекс: доступ к истории и режим сосуществования | Провайдер подтверждает credentials/точки/права/глубину без переключения действующей системы. |

После снятия блокеров объём реализации: отдельный payment adapter и журнал попыток/outbox, привязка устройств, доверенный результат + reconciliation и состояния POS; для пути A дополнительно Android APK, для пути B отдельный клиент/авторизация Мобильного кассира. Яндекс-аналитику делать отдельным read-only адаптером; операционный приём заказов считать самостоятельным этапом. Существующий `EvotorClient` оставить клиентом чтения.

Минимальные будущие проверки: двойное нажатие/push, таймаут после успешной оплаты, касса офлайн/занята чужим чеком, перезапуск APK, отказ банка, успех банка с ошибкой фискализации, поддельный/повторный callback, несовпадение суммы/точки и возврат. Для Яндекса: несколько страниц, граница окна, смена статуса, недоступные детали, повторный импорт и отсутствие двойного учёта. Живые платежи и provider writes только по отдельному разрешению; в рамках этого исследования проверена документация, не работа оборудования.
