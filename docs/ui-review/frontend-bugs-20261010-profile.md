# Profile, repeat-order, loyalty-card pass — 2026-10-10

## Verified click-path findings

- `RepeatOrderButton` wrote `karimoff_cart` directly and navigated to `/?checkout=1`. The mounted `CartProvider` retained its previous `lines`, and its hydration-only URL effect did not run again on SPA navigation. A later persistence effect could overwrite the new storage snapshot. The old button also used historical prices, product IDs as slugs, and omitted customization entirely.
- Repeat now calls a read-only, authenticated, `no-store` endpoint. The query first scopes the order to the current customer and paid/refunded history before reading its items. Only `item_type=food` lines are repeated: the historical delivery fee is excluded, while unavailable/null-product food lines remain explicit. Product lookup uses exact current IDs, active status, current prices, and current ingredient/group definitions.
- Modern configuration snapshots restore ingredient IDs, serving counts, selected group options, and item notes. Deleted choices or newly invalid group selections are not replaced with defaults. Historical extra-ingredient gram amounts without an original serving-count snapshot cannot safely establish a count if the serving size changed; those lines require configuration again.
- `replaceCart` constructs the complete replacement before changing shared state, replaces rather than appends, persists the new snapshot, and prevents a delayed initial hydration read from undoing it. Equal configurations merge using the same identity as `addItem`; unsupported quantities are never silently truncated.
- The user's agreed fallback is implemented: current valid items replace the whole basket and navigation opens `/checkout`. The active drawer lists each unavailable/invalid line with its name and reason. If no line can be restored, the empty basket and explicit warnings are shown; no payable order is invented. A failed lookup leaves the original cart intact. Omitted-item warnings persist across reload in snapshot-bound sessionStorage and remain visible while the cart is edited; clearing or replacing the cart removes the prior notice.

## Loyalty and provider presentation

- Actual-schema local QA found a second QR blocker: `getCurrentConsentState` uses `granted.eq.true,source_path.neq./checkout`, while the PostgreSQL compatibility adapter only understood `eq`. It returned a filter error, silently yielding no consent and incorrectly showing enrollment even for a current granted membership. The adapter now safely supports parameterized `neq` in OR, preserves dots in values, and rejects unsupported operators/unsafe identifiers. The existing consent predicate and membership gate are unchanged.
- The loyalty page keeps its existing membership gate, QR endpoint, signed token, and card lifecycle. Its duplicate large heading and introduction are replaced with a compact header.
- On mobile the QR is the first card content; balance and owner details follow it. On wider screens the prior balance/QR arrangement remains. QR quiet-zone background is explicitly white in both themes; the existing endpoint produces a black-on-white SVG.
- The security section reuses the existing Telegram SVG and approved MAX mark rather than letter placeholders, with provider blue/purple tiles.
