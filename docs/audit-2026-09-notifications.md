# Аудит уведомлений: 2026-09-08

## Решение

Операционный экран готов к локальной сборке и проверке; **реальные уведомления пока не активировать**. Массовые рассылки, персональные предложения, сообщения сотрудникам и SMS не реализованы и не включены.

Работа ограничена `src/lib/notifications/**`, новым `/admin/notifications`, профильными тестами и двумя документами. Общая навигация, auth, analytics, migrations, production, env и DB не изменялись этой задачей. Commit/push/deploy не выполнялись. Родительская задача подключила навигацию для owner/admin и выполняет Docker/browser smoke.

## Находки

| Приоритет | Находка | Результат |
| --- | --- | --- |
| P1 | Telegram Login сохранял `claims.sub`, но не отдельный подписанный `id`; provider использовал это как `chat_id` | Worker теперь использует только `metadata.telegramBotUserId` из проверенного `claims.id`, положительную safe-integer строку. Нет fallback на sub; отсутствие/ошибка даёт `telegram_recipient_unverified`. Parent/auth добавляет поле при обычном входе, не меняя `providerUserId`; DB migration и forced relink не нужны |
| P1 | Сохранение `sent` находилось в одном catch с POST: сбой БД после принятия мог вызвать повторную отправку | `markSent` вынесен из provider catch; сбой сохранения оставляет lease для проверки, не создаёт retry |
| P1 | Истёкшие processing lease автоматически отправлялись ещё раз; число попыток не ограничивалось на claim | Неизвестный результат изолируется в существующий terminal status; claim ограничен `<8`; legacy network/unknown retry и записи с признаком принятия также изолируются |
| P1 | Обрыв POST или неполный 2xx не позволяет знать, принято ли сообщение | Network/408/невалидный 2xx теперь terminal unknown, без автоматического или ручного повтора |
| P1 | Документ обещал отсутствие исторических отправок после включения | Исправлено: trigger не зависит от env; накопленный backlog требует отдельного решения до активации |
| P2 | MAX response разбирался как `body.mid`/`message_id`, мог сохраняться пустой успех | Проверяется официальный envelope `message.body.mid`; Telegram также требует непустой валидный ID |
| P2 | MAX без Retry-After превращал `null` в 0; Telegram игнорировал JSON error_code при HTTP 200 | Разбор исправлен; date/seconds поддержаны, отсутствующий/некорректный header даёт 30 s; backoff не сокращается ниже provider delay |
| P2 | Проверка identity не сверяла текущего владельца заказа/привязки | Добавлено равенство identity user, delivery customer и order customer перед POST и ручным retry |
| P2 | Fire-and-forget timer мог оставить unhandled rejection; maintenance не останавливал worker | Scheduler ловит сбой и снимает running; worker/provider учитывают maintenance и kill switch |

### Остаточные ограничения

- Уникальная запись в очереди не обеспечивает exactly-once на стороне провайдера. HTTP 5xx всё ещё автоматически повторяется как временный отказ, поэтому остаточный риск дубля принят как прежняя ограниченная политика, а не доказанная идемпотентность. До большого потока требуется отдельное решение по этому риску.
- Статус заказа/привязка могут измениться в промежутке между SELECT и внешним POST. Межсистемной атомарности нет; повторная проверка снижает риск, но не устраняет его.
- Unknown outcome намеренно предпочитает остановку повтору. Возможен пропуск уведомления после сбоя до POST; для него нет кнопки «отправить всё заново».
- Worker является таймером внутри процесса Next.js. Экран показывает состояние очереди, не наличие живого worker и не provider uptime. Реплики, перезапуски, ограничения платформы и устойчивость SQL concurrency нужно проверить отдельно.
- Очередь хранит `ready/cancelled` по каждой identity. Если подключены оба провайдера, возможны два сообщения. Нет предпочтительного канала, fallback, TTL или suppression-списка на провайдера.
- Счётчики агрегируют всю очередь; список ограничен 50 записями. Нет обещания полной истории/экспорта; для большого объёма нужен отдельный план retention и индексов после измерения.

## Экран и безопасный повтор

Новый маршрут: `/admin/notifications`. Использует существующие `server-only`, `getCurrentStaff`, `getPostgresSql`, `audit_logs` и принятый шаблон server action. Owner/admin разрешены, manager/cashier/cook запрещены; проверка не зависит от скрытой кнопки или навигации. Секреты и адресаты не передаются в HTML/RSC; ошибки отображаются только через фиксированный словарь.

GET получает только aggregate SELECT и ограниченный SELECT последних доставок; не запускает batch, не обращается к API провайдера и не пишет в БД. Refresh делает новый GET. Недоступная схема/БД отображается как отсутствие данных, а не пустая здоровая очередь.

Ручной retry разрешён только для preflight-сбоя **на первой попытке до HTTP**. Обязательны подтверждение одной записи, актуальный заказ, совпадающий владелец identity, исправная текущая конфигурация, включённая доставка, отсутствие maintenance, lease и признаков принятия. Только четыре кода: `app_origin_not_configured`, `telegram_not_configured`, `max_not_configured`, `telegram_recipient_unverified`. Последний допускает повтор лишь после появления корректного подписанного `metadata.telegramBotUserId` при обычном входе. Для всех Telegram повторов SQL повторно проверяет строковый формат ID и верхнюю границу `9007199254740991` с безопасным CASE, без fallback на sub. UPDATE сохраняет attempt budget и условно переводит одну запись в `retry`; audit insert входит в ту же transaction. Повторный клик после смены статуса не обновляет строку. Результат действия не обещает, что сообщение уже отправлено.

Отказ/блокировка провайдера, сетевой сбой, истёкший lease, исчерпанные попытки, второй или последующий конфигурационный сбой, `sent`, `superseded` и Telegram с непроверенным OIDC адресатом не подлежат ручному повтору. Нет bulk retry, редактора текста, выбора аудитории, тестовой отправки или переключателя включения.

## Возможности платформ

Сверено с официальной документацией 2026-09-08; это технические возможности, не подтверждение согласия конкретных клиентов.

- Telegram Bot API: `sendMessage` отправляет текст и inline keyboard, успешный результат содержит `Message`; ошибка имеет `ok=false`, `error_code`, иногда `parameters.retry_after`. [Bot API](https://core.telegram.org/bots/api#sendmessage).
- Telegram Login: SDK scope `write` и OIDC scope `telegram:bot_access` описывают право бота писать после входа. `sub` и профильный `id` описаны раздельно. `botAccessRequested=true` в metadata текущего кода является намерением запроса, а не подтверждённым согласием на рекламу. [Telegram Login](https://core.telegram.org/bots/telegram-login).
- Telegram рекомендует не более одного сообщения в секунду одному чату и около 30 сообщений в секунду для бесплатного broadcast. Paid broadcast не включён, `allow_paid_broadcast` не передаётся. [Bots FAQ](https://core.telegram.org/bots/faq#how-can-i-message-all-of-my-bot-s-subscribers-at-once).
- MAX: `POST https://platform-api2.max.ru/messages?user_id=...`, token только в `Authorization`, response содержит `message`; объект имеет `body`. Документация предупреждает о TLS-доверии сертификату Минцифры и лимите двух сообщений в секунду одному диалогу. `notify` относится к уведомлению внутри MAX, а не к отдельному web/mobile push-транспорту. [Отправка сообщений](https://dev.max.ru/docs-api/methods/POST/messages), [Message](https://dev.max.ru/docs-api/objects/Message).
- MAX предоставляет `bot_started` и подписки на события; существующую привязку нельзя считать доказательством бессрочной доступности пользователя. Перед активацией подтвердить запуск бота и нужные события отказа/отписки в контролируемом сценарии. [Подготовка бота](https://dev.max.ru/docs/chatbots/bots-coding/prepare).

## Шаги активации

Каждый шаг с внешним побочным эффектом требует отдельного разрешения. Ни один из них этим аудитом не выполнен.

1. **Оставить worker выключенным.** Утвердить владельца сервиса, каналы, транзакционные тексты, политику неизвестного результата и обработки backlog. Не использовать смену флага как тест.
2. Проверить существующую migration `20260828220000_add_order_status_notifications.sql`, grants/RLS, trigger и требуемые колонки в согласованном окружении. Миграцию не применять автоматически из экрана.
3. Включить в согласованный релиз изменение parent/auth: `metadata.telegramBotUserId` только из проверенного подписанного `claims.id` (положительный safe integer, сохранённый строкой). `providerUserId/sub` не менять. Старые identities обогащаются при следующем обычном входе; принудительная перепривязка, миграция БД и переписывание outbox не нужны. До этого их сообщения блокируются. Проверить связку ID с нужным ботом; `botAccessRequested` означает запрос, не выданное право. Отказы Bot API остаются terminal без повторов.
4. Настроить отсутствующий **Telegram Bot Token**, принадлежащий нужному боту. OIDC client ID/secret не являются заменой. Для MAX проверить токен и доверенную TLS-цепочку контейнера; не отключать проверку сертификатов. Убедиться в корректном HTTPS `APP_ORIGIN`.
5. Пока worker выключен, получить read-only счётчики и возраст backlog. Отдельно согласовать обработку старых pending/retry и cancelled; для исключения старых записей потребуется явно одобренная операция, которой нет на экране. Простое включение не гарантирует отсутствие старых отправок.
6. В изолированном staging выполнить поведенческие проверки SQL locks/CAS/rollback audit, двух worker, обрыва после POST и после сохранения, exhausted, unlink и смены владельца. Текущие unit tests используют подставные SQL/HTTP, не доказывают concurrency реального Postgres.
7. После явного согласия получателей выполнить по одной контролируемой доставке каждого события/канала с отдельными test bots. `is_test=true` заказы намеренно исключены: не ожидать сообщений от них и не обходить это ограничение в production. Проверить фактический адресат, сохранённый ID, отказ/блокировку и отсутствие дублей. Не включать общий production backlog ради canary.
8. Только после закрытия блокеров и отдельного разрешения включить обработчик в согласованном окружении/релизе, проверить его таймер и мониторинг. Следить за возрастом очереди, permanent/unknown, 429 и задержками. Возврат флага в `false` и остановка/restart worker являются kill switch, но уже начавшийся POST отозвать нельзя.

## Архитектура согласий

Ниже требования к будущей реализации, не существующий механизм и не юридическое заключение. Продуктовые/правовые основания отдельно согласовываются перед запуском.

### Три независимых назначения

- **Статусы заказа:** только `ready/cancelled`, без рекламных вставок. Проверенный адресат и право писать этому пользователю. Существующий outbox сохраняется узким; отказ от рекламы не должен автоматически отменять необходимый сервисный статус.
- **Персональные предложения и рассылки администратора клиентам:** отдельный добровольный opt-in, цель marketing, канал Telegram/MAX, конкретный бот, версия текста согласия, время/источник выдачи и отзыва. Отдельно определить разрешённую персонализацию по истории покупок. Наличие профиля, заказа, phone consent или bot write access не заменяет такой выбор.
- **Операционные push сотрудникам:** отдельные staff subscriptions, права/точки, события, расписание и индивидуальный отказ. Не смешивать customer identities с сотрудниками. Web/mobile push, если он действительно нужен, требует отдельной подписки и разрешения ОС/браузера; этот транспорт не реализован.

### Данные и отзыв

В проекте уже есть журнал `legal_consents` с общим `marketing` и пользовательский выбор, развиваемый parent/auth. Нельзя выводить разрешение на все каналы/боты из любой исторической строки `granted=true`: учитывать последний действующий выбор и отзыв. Для будущих кампаний требуется привязать доказательство к customer + identity + provider + bot + purpose + policy version и поддержать suppression при блокировке/отписке, relink и удалении аккаунта.

Проверять согласие и suppression при построении аудитории **и непосредственно перед отправкой каждой записи**. Отзыв должен исключать ещё не отправленные элементы, включая retry и запланированные кампании. Хранить минимум доказательств и метаданных, без raw tokens/payload, с отдельными правами и сроком хранения. Для персонализации использовать только утверждённые признаки, без чувствительных выводов.

### Кампании и защита от массовой отправки

Будущий отдельный campaign outbox: `draft -> preview -> approved -> scheduled -> sending -> paused/completed/cancelled`, неизменяемый текст и аудитория утверждённой версии, dedup key на campaign/recipient/channel, test audience и раздельный kill switch. Никаких записей кампаний в `order_notification_deliveries`, искусственных событий заказа или автоматического заимствования всех identities.

До запуска обязательны предпросмотр персонализации, число получателей и причина исключения, ограниченный тест, явное подтверждение уполномоченным сотрудником, аудит инициатора и версии. Нужны общие лимиты для всех реплик, per-recipient rate limits, частотные ограничения, тихие часы, остановка и отзыв в очереди. Платный Telegram broadcast и расширение объёма требуют отдельного согласования. Отсутствие любого opt-in/разрешения приводит к исключению, а не fallback на SMS или другой канал.
